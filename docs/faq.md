# 常见问题

## 一份 OFD-H 是患者全部病历的集合吗？

DocPaw-OFDH 一次处理一份业务文书的一个来源版本，例如一份入院记录或检验报告。多份文书之间的索引、就诊关联和归档集合由业务系统维护。患者标识与文件标识分别记录。

## 已有 OFD 导出能力，还需要这个项目吗？

可以使用 `ofdh-core` 保留现有页面及资源，补充 OFD-H 文档类型、元数据、来源信息和可选机读附件，并生成检查报告。接入方无需引入 PDF 转换依赖。

## 只有 PDF，是否还需要模板设计器？

受支持的静态 PDF 已经包含版式，工具通过其文字、字体、图形和坐标生成 OFD，这条路线无需重新制作模板。扫描图像或当前不支持的 PDF 特性，需要先改善导出或另行实现转换适配。

## PDF 没有显示诊断编码，可以把编码放入机读数据吗？

可以。页面呈现和临床机读数据是两个层次。接入方可以提供来源系统中的诊断名称及代码，按 Schema 保存到 JSON，无需为增加该字段而改动 PDF 文字坐标。工具检查结构及已声明的来源一致性，代码真实性和医学语义由业务侧确认。

## 是否需要按项目结构修改医院数据库？

核心工具不访问数据库。宿主将文档元数据映射到请求对象，临床正文可以采用内置 Schema，也可注册自己的本地 Schema。字段取数、字典和版本锁定留在接入层。

## 可以嵌入传统 Java Web 或 WinForms 系统吗？

Java 服务可引用 SDK，字节码目标为 Java 8；实际依赖冲突需在宿主核对。WinForms 或其他语言可以调用独立 CLI，按 JSON 输出、退出码及摘要处理结果，见 [接入说明](integration.md)。

## 医院的 CA 不在项目中，怎么办？

完整 OFD 签章服务实现 `SignProvider`；基础 SM2 签名服务通过 `Sm2Signer` 返回签名值。项目负责 OFD 封装，院方适配层负责授权、身份和通信协议。当前签名及验签范围为受支持的 SM2/SM3 数字签名，见 [CA 接入](ca-integration.md)。

## 为什么生成成功，检查仍然是 INCOMPLETE？

文件可能已完成封装，但仍缺签署、证书信任、独立视觉验证或完整线性化等证据。报告列出逐项结果和未覆盖范围，`INCOMPLETE` 不能用作标准符合性证明。

## 页面顺序优化是否等于完整线性化？

当前优化将页面及模板、字体、图像等依赖按阅读顺序前置，保留普通 OFD/ZIP 容器。它可用于具备相应部分读取能力的阅读端；完整线性化协议及跨厂商符合性需要另行证明，见 [页面布局](page-order.md)。

## 可以改写已签署 OFD 吗？

已签文件可以检查，不能交给 `prepare` 改写；当前也不支持追加签名。内容变更应形成新的业务版本，按授权流程重新生成，历史文件及签署记录由原系统保留。

## 错误后能否直接重试？

先判断已完成阶段。字段或格式错误需修正输入；文档已生成但报告失败时应补报告；远端 CA 超时需先查询任务状态。重复生成可能得到新的文件标识和摘要，输出不会覆盖，见 [错误处理](errors.md)。

## 可以用于生产吗？

当前为工程预览。采用方应使用自身授权材料核对来源兼容、逐页显示、机读数据、CA 及独立验签、归档和故障恢复。自动化测试覆盖不等于这些环境已验收，见 [能力与兼容性](implementation-status.md)。
